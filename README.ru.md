# MiWiFi для Home Assistant

[English documentation](README.md)

Локальное отслеживание клиентов сети и управление поддерживаемыми функциями
роутеров Xiaomi/Redmi с MiWiFi. Интеграция обращается к LuCI API роутера:
облачная учётная запись, LLM и внешний прокси для этого не нужны.

Это форк проекта [dmamontov/hass-miwifi](https://github.com/dmamontov/hass-miwifi).
Автор исходной интеграции — **Dmitry Mamontov**. Развитие этого форка ведётся
в [VascoRodriges/hass-miwifi](https://github.com/VascoRodriges/hass-miwifi);
исходная архитектура и поддержка моделей принадлежат upstream-проекту.

## Версия и совместимость

- Код в `main`: **4.0.2**. Опубликованный релиз на момент обновления инструкции:
  **v4.0.0**. HACS может предложить именно старый релиз, а не новый backend.
- Минимальная версия HA, заявленная для установки через HACS: **2026.9.4**.
- Работа на настоящем устройстве проверялась на **Xiaomi Router AX6000 (RA72)**
  с HA **2026.9.4**, прежде всего чтением состояния. Отказы и потенциально
  влияющие на работу сети команды проверяются на имитациях, а не отключением домашней сети.
- Требуется оригинальная MiWiFi-прошивка или прошивка с совместимым LuCI API.
  Наличие модели в upstream-списке не означает повторную проверку в этом форке.
  Совместимость с OpenWrt и произвольными сторонними прошивками не заявляется.
- Это custom integration, а не встроенная интеграция HA и не сертифицированный
  уровень Home Assistant Quality Scale.

## Что добавлено и зачем

- Корректные идентификаторы новых клиентов и защита от повторного добавления.
- Раздельные текущий IP и DHCP-резервация: смена резервации не подменяет старую аренду.
- Управление с optimistic-откликом, проверкой состояния у роутера и откатом при отказе.
- Последовательное выполнение изменений и опроса, чтобы устаревший ответ не затёр
  новое состояние. После потери ответа повторяется только чтение, не команда записи.
- Расширенные атрибуты клиентов: WAN-доступ, DHCP, QoS и состояние последней операции.
- Асинхронное ограниченное обнаружение web-портов, отмена задач при выгрузке.
- Безопасная очистка старых записей: предварительный просмотр и отдельное подтверждение.
- Редактирование секретов и клиентских идентификаторов в диагностических выгрузках.
- Полные описания 20 действий и read-only проверка возможностей `get_capabilities`.

Интеграция предоставляет сущности и действия. Готовая пользовательская панель,
карточки группировки клиентов, голосовой агент и его правила доступа **не входят**
в поставку. Их можно построить отдельно на этих сущностях и сервисах.
Домашних имён, MAC, IP-диапазонов и allowlist в публичной сборке нет.

## Установка

### Через HACS

1. В HACS откройте меню пользовательских репозиториев / Custom repositories.
2. Добавьте `https://github.com/VascoRodriges/hass-miwifi`, тип **Integration**.
3. Найдите MiWiFi, скачайте нужную доступную версию и перезапустите **Home Assistant Core**.
4. Проверьте версию в `config/custom_components/miwifi/manifest.json`.

Если HACS предлагает только v4.0.0, это не установка описываемого backend 4.0.2.
Не создавайте предположение о версии по названию репозитория. Если нужная ветка
не предлагается, используйте ручную установку из `main`.

### Вручную

1. Сделайте резервную копию существующей интеграции и конфигурации HA.
2. Скачайте [архив `main`](https://github.com/VascoRodriges/hass-miwifi/archive/refs/heads/main.zip)
   или подходящий опубликованный релиз.
3. Скопируйте каталог `custom_components/miwifi` в `config/custom_components` вашего HA.
4. Проверьте `manifest.json` и перезапустите **Core**.

Не устанавливайте upstream и этот форк одновременно под одним доменом `miwifi`.
После замены Python-файлов одного reload интеграции недостаточно. Для установки
не требуется перезапускать роутер или Home Assistant OS.

## Первая настройка

1. Убедитесь, что роутер имеет постоянный LAN IP и его локальный административный
   API доступен из сети HA. Один успешный ping не доказывает доступность API.
2. В HA откройте **Настройки → Устройства и службы → Добавить интеграцию → MiWiFi**.
3. Введите LAN IP и **локальный пароль администратора роутера** — не WiFi-пароль
   и не пароль Xiaomi-аккаунта.
4. Начните с `sha1`. Выбирайте `sha256`, если этого требует ваша прошивка.
5. Оставьте начальные параметры и проверьте чтение состояния.

Настройки по умолчанию:

| Параметр | Значение / назначение |
|---|---|
| Отслеживание клиентов | Включено |
| Опрос | Каждые 30 секунд |
| Timeout запроса | 20 секунд |
| Дополнительное удержание online | 0 секунд |
| Порог старой записи | 30 дней; это не автоматическое удаление |
| Очистка из настроек | Только preview, ничего не удаляет |

Часть конфигурационных сущностей выключена по умолчанию или не создаётся при
отсутствии обнаруженной поддержки: гостевой WiFi, каналы, мощность передатчиков,
диагностические сенсоры. При необходимости включите обнаруженную сущность
в настройках сущностей HA. Не уменьшайте интервал опроса без необходимости.

## Состояния и ограничения

Optimistic-обновление публикует желаемое значение **после предварительного чтения**,
до окончания записи и её подтверждения. Запрос, ожидающий другую операцию или опрос,
сначала ждёт очередь. Само изменение интерфейса не считается доказательством успеха.

`operation_status` показывает:

- `pending` — идёт выполнение/проверка;
- `confirmed` — состояние подтверждено;
- `failed` — свежее состояние отличается от запрошенного;
- `unknown` — получить подтверждение не удалось.

При отказе показывается прочитанное состояние; при недоступности чтения — последнее
подтверждённое с отметкой неопределённости. Неопределённые органы управления роутером
становятся unavailable до успешного опроса. `operation_id` и `pending` дополняют статус.
У клиента отображается последняя записанная операция, не постоянная история заданий.

Важные различия:

- `ip` — наблюдавшаяся аренда, `bound_ip` — DHCP-резервация. Новый адрес может начать
  действовать только после обновления аренды самим устройством.
- Атрибут tracker `online` — длительность соединения, не boolean. Действие
  `get_client_status` отдельно возвращает boolean/unknown `online`.
- Private/randomized MAC может создать новую клиентскую идентичность. Интеграция
  не определяет владельца телефона по имени модели автоматически.
- WAN-блокировка запрещает доступ через этот роутер, не мобильный интернет,
  другой шлюз или новый MAC.
- Для клиентского QoS требуется читаемая запись нужного MAC в `qos_info`.
  Пустой список не означает «без ограничений»; при невозможности проверки записи нет.
- `set_band` использует глобальные Mbps-поля, `set_qos` — клиентские KB/s-поля,
  заявленные интеграцией. Уточняйте данные вашей прошивки, не смешивайте единицы.

## YAML-примеры

Это примеры последовательностей HA-скриптов. Замените `ROUTER_DEVICE_ID` на ID
**устройства роутера в HA**, не на entity_id или IP. MAC в примерах вымышленный.
Не выбирайте tracked-клиента вместо роутера. Старый формат с одноэлементным
списком `device_id` также поддерживается.

### Прочитать возможности и статус клиента — без изменений настроек

```yaml
sequence:
  - action: miwifi.get_capabilities
    data:
      device_id: ROUTER_DEVICE_ID
    response_variable: router_capabilities
  - action: miwifi.get_client_status
    data:
      device_id: ROUTER_DEVICE_ID
      mac: "02:12:34:56:78:90"
    response_variable: client_status
```

`get_capabilities` проверяет поддержку **чтения**, не гарантирует поддержку записи.
На проверенном AX6000 RA72 чтение WiFi-расписаний недоступно. Список всех 20 действий
и endpoints находится в [английском описании](README.md#services).

### Заблокировать WAN — это уже изменение настройки роутера

Сначала подтвердите MAC конкретного клиента и исключите инфраструктуру.
`wan: 0` блокирует, `wan: 1` восстанавливает доступ.

```yaml
sequence:
  - action: miwifi.set_mac_filter
    data:
      device_id: ROUTER_DEVICE_ID
      mac: "02:12:34:56:78:90"
      wan: 0
    response_variable: result
```

`result.verified: true` означает проверенное WAN-разрешение роутера,
а не сетевую проверку реального интернет-соединения.

### Предпросмотр очистки — ничего не удаляет

```yaml
sequence:
  - action: miwifi.cleanup_stale_clients
    data:
      device_id: ROUTER_DEVICE_ID
      days: 30
      dry_run: true
    response_variable: preview
```

Изучите `preview.candidates`. Для реального удаления нужен **отдельный** вызов
с `dry_run: false` и `confirm: true`. Сделайте backup HA. Удаляются подходящие
записи интеграции/реестров HA, не устройства и не DHCP-резервации на роутере.
Online-клиенты, резервации и устройства других интеграций защищены от очистки.

`response_variable` поддерживается действиями с ответом, но не всеми действиями
управления: не добавляйте его автоматически к любой команде.

## Экспериментальные функции

`set_wifi_timer`, `set_mac_time`, `add_mesh_node`, `set_wifi_macfilter`
зависят от прошивки и возвращают только `acknowledged: true, verified: false`.
Это подтверждение ответа API, **не** применения расписания, mesh-пары или фильтра.
WiFi-расписание сначала проверяет доступность read endpoint; неподдерживаемый
endpoint останавливает действие без отправки расписания.

Потеря ответа вызывает ошибку; запись автоматически не повторяется. Не передавайте
эти функции голосовому агенту как инструменты с гарантированным результатом.
Raw-действие `request` ограничено allowlisted-чтением, не обходом проверок записи.

## Голосовое управление и приватность

Для Assist настройте отдельные узкие скрипты с явным allowlist клиентов.
Свяжите понятные имена с проверенными MAC, исключите роутер, HA и серверы,
а опасные операции выполняйте с подтверждением. Готового LLM-агента в MiWiFi нет.
Не предоставляйте LLM неограниченную прошивку, cleanup, общесетевые фильтры и raw API.

Debug и диагностические выгрузки редактируют секреты и клиентские поля. Однако
обычные сервисные ответы и события `miwifi_luci` могут содержать IP, MAC, имена
и другие приватные данные: диагностическая редактура не распространяется на них.
Проверяйте содержимое перед публикацией в issues или логах.

## Проверки и известные предупреждения

- 66 backend/client regression tests без доступа к оборудованию и LAN.
- CI настроен на Python 3.14 / HA 2026.9.4; локальные regression tests также
  выполнялись на HA 2026.7.4, что не доказывает полную совместимость старых установок.
- Старый upstream pytest suite не является частью текущего CI форка.
- HA 2026.9.4 может предупреждать об использовании `device_registry.async_get_device`.
  Переход на новый API нужен до объявленного удаления в 2027.8; совместимость
  с этой будущей версией не заявляется.

Для сообщения об ошибке укажите версии HA/интеграции, модель и firmware роутера,
а также очищенную ошибку. Не публикуйте пароли, токены и необработанные ответы API.
Issues этого форка: [VascoRodriges/hass-miwifi/issues](https://github.com/VascoRodriges/hass-miwifi/issues).
